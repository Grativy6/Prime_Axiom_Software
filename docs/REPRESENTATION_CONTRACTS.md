# Representation and machine contracts

## 1. Shared floor

`BitState` is a two-valued, readable abstract state. It is the shared implementation floor, not an ontological or physical claim. A host enum stores it, but arithmetic circuits may inspect it only through gate constructions when reporting gate-level work.

`NandGate` is represented by `GateNetwork.Nand`. All derived combinational logic is assembled from NAND calls. A `GateCost` contains:

- `NandEvaluations`: exact calls made by this logical implementation;
- `CriticalPathDepth`: maximum unit-NAND dependency depth under the model.

Those fields do not denote transistor count, relay count, area, power, energy, or elapsed time.

The sequential model admits feedback explicitly. `SrNandLatch` reports `Stable`, `ForbiddenInput`, or `DidNotSettle`. It does not invent a value for analog metastability. `BinaryRegister` is an array of gated D latches; `BinaryCounter` uses the same gate-level adder and register path as ordinary binary state.

## 2. Conventional representations

### Unary register

A unary register stores quantity as the number of `On` cells. Cell position is address metadata, but no positional weight is assigned. Increment changes one available mark; capacity is linear in the represented maximum. It is a control representation, not the proposed scalable machine.

### Binary word

`BinaryWord` is a fixed-width, least-significant-bit-first vector. Interpretation as unsigned magnitude is explicit. The following are not silent:

- width;
- truncation boundary;
- carry or borrow;
- multiplication output width (`2w`);
- conversion to or from a semantic `BigInteger` oracle.

The gate-level operations are `ADD`, `SUBTRACT`, `COMPARE`, `MIN`, `MAX`, `INCREMENT`, and transparent shift-and-add `MULTIPLY`.

## 3. Prime basis and semantic identity

A `PrimeBasis` is a finite, ordered configuration of labels that have been checked as ordinary primes. The runtime exponent payload does not contain those labels; dense lane identity resides in position/wiring. Consequently two costs must remain distinct:

- resident payload cost: exponent bits per value;
- catalogue/configuration cost: the labels, their certification/provenance, and any routing or table needed to interpret lane positions.

If the labels are treated as opaque generators, exponent-vector composition still defines a free commutative monoid. It becomes ordinary positive-integer arithmetic only after the configured evaluation map assigns the generators to actual primes. Prime identity is therefore not below distinction or identity; it is a semantic layer above them.

## 4. Dense positive prime coordinates

`PrimeCoordinates` has one fixed-width binary exponent word per configured prime:

```text
value = product over lanes i of basis[i] ^ exponent[i]
```

Its exact domain is the positive integers generated by the configured basis, subject to exponent width. Contracts:

- `1` is the all-zero exponent vector;
- `0` is outside the positive coordinate domain;
- negative sign is outside the positive coordinate domain;
- a factor not in the basis returns `BasisEscape` with an unrepresented residual carried in both direct encoding results and crossing/VM receipts;
- an exponent outside the lane width returns `ExponentOverflow`;
- basis and exponent width are part of representation identity;
- no failed operation silently stores a truncated result.

`TaggedPrimeValue` adds explicit zero and sign states. Zero has no factor vector. This keeps zero distinct from the all-zero vector for `1`.

### Coordinate-local operations

These operations use only exponent payload plus fixed basis identity:

| Instruction | Coordinate action | Failure/state |
|---|---|---|
| `COMPOSE` | lane-wise exponent addition | exponent overflow |
| `CANCEL` | lane-wise subtraction | not divisible / underflow |
| `MEET_GCD` | lane-wise minimum | basis/width mismatch |
| `JOIN_LCM` | lane-wise maximum | basis/width mismatch |
| `DIVIDES` | lane-wise partial-order check | basis/width mismatch |
| `PROJECT` | read one exponent lane | address decode not modeled |

Every lane uses ordinary bounded binary arithmetic. The model has moved multiplication of magnitudes into a parallel bank of exponent adders; it has not removed addition or carry. `COMPOSE` and `CANCEL` also charge a balanced NAND reduction of lane carry/borrow flags, and `DIVIDES` charges both comparison and final status logic.

### Explicit crossings

| Operation | Crossing that must be paid |
|---|---|
| `ENCODE_BY_FACTORIZATION` | magnitude to basis coordinates by trial remainder/division |
| `RECONSTRUCT` | coordinate powers to ordinary magnitude |
| `ADD_VIA_RECONSTRUCT_REFACTOR` | reconstruct both operands, add magnitudes, factor result |
| numeric order | not implemented as coordinate order; requires reconstruction or a certified global comparator |

The receipt records whether the magnitude domain was used and separately counts trial remainders, factor divisions, reconstruction multiplications, magnitude additions, actual completed lane reads/writes, and gate work. These are operation counts, not bit-complexity or energy estimates. No conversion is charged as zero merely because the call is compact.

## 5. Sparse coordinates

`SparsePrimeCoordinates` stores sorted `(lane index, positive exponent)` pairs and omits zero lanes. It is canonical only under a fixed basis and sorted unique lane indices.

Sparse composition is a merge. Its current receipt counts:

- lane-index comparisons;
- exponent additions for matching lanes;
- output entry writes.

These are abstract data-structure operations, not NAND-equivalent counts. Payload estimates include lane indices, exponent fields, and an optional length header. Real implementations would also pay capacity, allocation, alignment, tags, and catalogue storage.

Dense and sparse forms make different trades:

- dense lanes offer fixed routing and parallel depth but pay every lane for every value;
- sparse form pays only nonzero support but requires identity metadata, merging, routing, and variable-length storage.

## 6. Minimal experimental VM

The VM is justified only as a narrow probe of the coordinate domain. It is not proposed as a general instruction set.

Native instructions:

- `LOAD_CERTIFIED`: accept an already verified exponent certificate;
- `COMPOSE`, `CANCEL`, `MEET`, `JOIN`, `PROJECT`.

Boundary instructions:

- `LOAD_MAGNITUDE`: factor an ordinary magnitude into the configured basis;
- `RECONSTRUCT`: emit ordinary magnitude;
- `ADD_REFACTOR`: leave the local domain, add, and refactor.

`LOAD_CERTIFIED` refuses a caller-declared unverified certificate. The VM does not manufacture factor provenance. A program stops on the first failure by default and retains a step receipt.

## 7. Equality, order, and information

Canonical coordinate equality is exact map equality. Divisibility is coordinatewise. Numeric order is different: it depends on the weighted global quantity `sum e_p log(p)` or exact reconstruction and must not be inferred from componentwise order.

Exact magnitude and exact prime coordinates are bijective on a declared covered positive domain. Neither intrinsically loses information. Both addition and multiplication are many-to-one if their operands are discarded; both are injective in one positive operand when the other is fixed. Reversibility claims must account for retained inputs, history, ancilla, or quotient/remainder information.

## 8. Fair-comparison rules

- Compare machines over the same semantic input/output domain.
- Charge a dense basis for every lane required to cover that domain.
- Charge sparse values for indices and length/capacity metadata.
- Report catalogue cost separately when it is amortized rather than pretending it is absent.
- Match parallelism before drawing latency conclusions.
- Separate ingress, resident operation, and egress.
- Do not compare a transparent logical model with an optimized host primitive as if they were the same cost class.
- Preserve overflow, basis escape, invalid input, and unsupported operation as distinct results.
